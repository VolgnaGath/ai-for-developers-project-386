# План реализации backend

## Стек

- Node.js 24 LTS.
- TypeScript.
- Express 5.
- `@nahkies/openapi-code-generator` для генерации router, типов и runtime-валидации из OpenAPI.
- Zod для сгенерированной runtime-валидации.
- `@js-temporal/polyfill` для календарной логики.
- Vitest + Supertest.
- In-memory `Map` для типов событий и броней.

Цепочка остаётся contract-first:

```text
main.tsp
  -> npm run generate
  -> tsp-output/schema/openapi.yaml
  -> генерация backend router/types/validators
  -> ручная реализация бизнес-логики
```

Express здесь только запускает сгенерированный router. Маршруты, параметры, тела, статусы и ответы не дублируются вручную.

Официальный `@typespec/http-server-js` пока alpha/preview, поэтому его не используем как основу проекта.

## Принятые решения

- `from` и `to` включительны.
- Окно бронирования: сегодня и следующие 13 календарных дней в `PublicConfig.timezone`.
- Прошедшие старты текущего дня исключаются.
- Кандидаты начинаются каждые `slotStepMinutes` (15 минут).
- При длительности 30 минут кандидаты могут пересекаться.
- Любая бронь блокирует пересекающиеся слоты всех типов событий (общая занятость владельца).
- Пересечение определяется по полуинтервалам `[start, end)`.
- После запуска создаются демонстрационные типы событий (seed), но не брони.
- Backend возвращает слоты и брони хронологически.
- API timestamps возвращаются в UTC; frontend сам отображает их в таймзоне конфига.

## Уточнение контракта

Перед backend поправить `main.tsp`:

- Добавить `BadRequest` с `400` и `code: "bad_request"`.
- Добавить `400` операциям с body/query validation.
- Зафиксировать включительность `to`.
- Описать окно как 14 календарных дат.
- Убрать утверждение, что возвращаемые кандидаты никогда не пересекаются.
- Явно указать общую занятость владельца.
- Добавить `@minLength(1)` для `EventTypeInput.title`.
- Зафиксировать: `422` означает, что старт не является базовым кандидатом; `409` означает, что корректный кандидат уже занят.
- Перегенерировать OpenAPI и frontend-типы.

## Структура

```text
backend/
├── src/
│   ├── generated/        # router, API-типы, Zod-схемы
│   ├── app.ts            # Express, CORS, error mapping
│   ├── server.ts         # PORT и запуск
│   ├── config.ts         # фиксированная доступность
│   ├── store.ts          # in-memory Map и seed
│   ├── calendar.ts       # генерация и проверка слотов
│   └── handlers.ts       # реализация operationId
├── test/
├── package.json
└── tsconfig.json
```

Дополнительные слои и repository-интерфейсы пока не нужны. `store.ts` можно заменить адаптером БД позднее.

## Ключевой алгоритм

Для получения слотов:

1. Найти тип события или вернуть `404`.
2. Проверить диапазон дат.
3. Пересечь его с окном бронирования.
4. Для рабочих дней построить старты с шагом `slotStepMinutes`.
5. Оставить слоты, полностью помещающиеся в рабочие часы.
6. Исключить прошедшие старты.
7. Исключить кандидаты, пересекающиеся с любой бронью.
8. Вернуть результат хронологически.

Для создания брони:

1. Найти тип события или вернуть `404`.
2. Проверить входной старт как базовый кандидат без учёта занятости.
3. Если старт не соответствует сетке, окну или рабочим часам, вернуть `422`.
4. Атомарно проверить пересечения со всеми бронями.
5. При пересечении вернуть `409`.
6. Без `await` между проверкой и добавлением создать бронь.
7. Рассчитать `end`, `createdAt`, `status` и ID на сервере.

Такая операция атомарна для одного Node.js-процесса. Несколько реплик с in-memory storage запускать нельзя.

## Этапы реализации

1. Уточнить TypeSpec и перегенерировать OpenAPI.
2. Добавить `backend` как npm workspace.
3. Настроить генерацию backend-кода из OpenAPI.
4. Реализовать config, clock abstraction и in-memory store с seed.
5. Реализовать календарную логику чистыми функциями.
6. Подключить handlers ко всем `operationId`.
7. Настроить CORS через `FRONTEND_ORIGIN`.
8. Добавить unit-тесты календаря и пересечений.
9. Добавить HTTP integration-тесты всех статусов из контракта.
10. Проверить готовый frontend с реальным backend вместо Prism/MSW.
11. После этого добавить multi-stage Dockerfile на Node.js 24 Alpine.

Особенно важные тесты: границы рабочего дня, выходные, смена DST, конец 14-дневного окна, пересечения 15/30 минут, разные типы событий, двойное бронирование и удаление типа с бронями.

## Проверка результата

- TypeSpec компилируется без ошибок.
- OpenAPI и сгенерированные backend-типы/router синхронизированы.
- Backend проходит typecheck, unit-тесты и integration-тесты.
- Все статусы из контракта покрыты тестами: `200`, `204`, `400`, `404`, `409`, `422`.
- Гостевой и административный сценарии фронтенда работают с реальным backend.
- Backend запускается в Docker.
